# 成员操作与确认

AO 的所有成员遵循同一原则：已授权的日常读取、聊天与办公室协作自动继续；需要新增授权或无法判断的操作说明具体原因，由本人决定。成员、房间或项目的原有授权继续有效，消息内容和模型口头声明不扩张权限。

需要确认时，卡片出现在对应成员的最新对话位置，带当前任务、原因和选择按钮。原生提问的建议选项可直接点选，也可自行填写；提交回答后才返回客户端，点选本身不执行操作。具体命令可展开核对。确认结束后卡片移除，阅读历史时不强制跳回底部。办公室视图的提示可直接定位最新确认。接入秘书成功会收起接入页与教程，进入办公室；失败、过期请求或其他房间的接入结果不会带走当前页面。

各客户端使用其实际支持的执行边界：

| 入口 | 日常操作 | 风险或权限不足 |
| --- | --- | --- |
| Codex 后台 | 使用原生自动风险审查，保留项目 sandbox 与 on-request | 显示原生审查原因；真实人工请求在成员对话中选择。原生拒绝不能伪造为已允许 |
| Claude Code、Qwen Code、Gemini CLI | 已授权的只读工具和 AO 协作工具自动处理 | 超出工具范围的原生拒绝也显示在同一成员对话中；当前非交互协议没有执行中审批接口，不制造无效的“允许”按钮 |
| Qwen、豆包原生桌面对话 | 已接通人物可自动收发，使用同一协作规则 | 客户端自身工具权限仍由其真实接口处理；没有执行前回调的功能不能冒充 AO 已审批 |
| 其他客户端 | 按已验证的适配器能力执行 | 不把检测到进程或写入配置当成后台执行与审批能力 |

人工等待不会消耗 Codex 的模型执行超时；取消仍等待原生结束确认，确认缺失则保留“结果待核对”，不重新提交。多个待办全部完成前仍显示等待确认。过期 turn、其他客户端的请求或已结束请求不会成为当前人物的新审批。

AO 的独立 Codex 配置只保留已有 Windows 沙箱实现选择（elevated/unelevated），不会复制个人全权限模式或关闭审批。该选择不等于沙箱已完成系统配置，也不证明共享盘访问一定可用。

依据：[OpenAI 自动风险审查](https://learn.chatgpt.com/docs/sandboxing/auto-review)、[App-server 审批协议](https://learn.chatgpt.com/docs/app-server#approvals)、[Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)。
