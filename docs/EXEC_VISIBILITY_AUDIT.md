## 对 Grok 解释的判断

- “调用的是后台 CLI”与记录一致。
- “运行完成后进程结束”符合 exec 使用方式。
- “结果只回到 Grok”描述了本次调用的直接输出去向；同时，保存的会话及回答已经能独立读取，不能据此推断记录不存在。
- “本次没有在桌面看到实时反馈”仍需观察桌面行为，不能仅由 exec 推断根因。
- “改用可管理的会话接入”是合适方向，但新建 App Server 线程也不自动证明桌面项目归属和实时订阅已完成。

[官方非交互文档](https://developers.openai.com/codex/noninteractive)支持恢复 exec 会话，只有使用 ephemeral 才主动不保存 rollout。[App Server 文档](https://developers.openai.com/codex/app-server)说明，未显式设置 sourceKinds 时，列表默认面向 cli、vscode 等交互来源；exec 是单独的来源类别。这是显示差异的候选原因，尚未证明本机桌面实际采用了哪个筛选。

## 建议下一步

优先将第二条成功会话绑定为本项目的 Grok 专用问答讨论。复用精确 ID，核对版本、工作目录与权限，随后验证命名、桌面项目显示、同会话追问及流式反馈。不要因会话没显示就再次创建。

中文传递需要单独修复：通过参数数组或明确的 UTF-8 stdin 传递并核对输入文本，而不是依赖未经确认的 shell 编码。第一次回答本身只能证明发生了乱码，尚未定位具体编码层。

当前已证明后台调用、记录持久化和独立读取；尚未证明桌面可见性、持续会话协作及 Grok 回调。
