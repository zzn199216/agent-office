# Grok 桥接连接诊断

## 在软件里继续接入

已配置的 Grok 加入新办公室时，AO 优先复用原人物、长期入口和已有通知渠道，不需要重新粘贴或配置。页面会说明「沿用已有连接」，这与本次重新验证成功分别显示。已有固定群桥接保留原路由，不能当作另一个人物改绑。

首次接入或确实需要恢复本人连接时，打开「连接 Grok Bot」，主界面直接显示以下步骤：

1. 点击「复制给 Grok 的接入说明」。
2. 将复制的整段说明发给你要接入的 Grok Bot。若 Grok 请求这台电脑的本机执行授权，在 Grok 内确认；让它按说明实际完成连接。
3. 保持 AO 页面打开。AO 自动检查这位 Bot 的实际握手，确认后进入办公室。

连接一个 Bot 不需要先建立 Grok 群，也不用手填房间 ID、MCP JSON 或调试端口。只有你另行要求原生群聊时，才处理群聊步骤。

当前 Grok 以本人窗口桥接接入。连接成功表示它的本机入口已验证；是否能持续后台响应取决于 Grok 自己的执行宿主，不能把这个状态显示成已自动接管。缺少电脑工具或授权时，Grok 需要在自己的窗口说明具体缺项。诊断详情放在可选的高级区域。

Agent Office 0.13.0 右侧“连接”页提供只读诊断。它只检查当前实例和你选定的房间，不扫描进程、不拉起模型、不重新发问、不创建群或成员。诊断摘要可以复制，不包含入口卡正文、密钥或带凭据的 MCP URL。

## 先区分四条链路

| 层级 | 本机能检查的证据 | 仍需在 Grok 核对的事项 |
| --- | --- | --- |
| Agent Office 本机服务 | 当前 HTTP 响应、实例标识、数据目录，以及所选房间是否存在 | 这不证明 Grok 有执行 Windows 本机命令的能力 |
| 房间成员与长期入口 | 实际成员关系、入口文件是否存在、既有凭据是否有效、真实握手记录 | 旧提示词里的成员标识是否仍指向这个实例中的实际成员 |
| Grok 注册的 Windows 电脑 | 本机没有独立读取 Grok 宿主状态的接口，诊断标为“需在 Grok 核对” | 电脑是否连接、是否获本机工具授权、当前 Bot 能否使用该宿主 |
| Grok 原生群与工具 | 本机保存过的群引用及 `host_reported` 报告，仅是宿主报告 | 实际目标群、Bot 身份、原生建群或加群工具是否可用；不按同名群猜测 |

可选的 **Webhook 通知** 是另一条链路：它用于本机主动通知一个指定 Grok 例程。Webhook 已配置、Agent Office 服务在线，均不能证明 Grok 的 Windows 宿主已连接。Grok 主动使用获授权的本机工具调用长期入口也不必依赖 Webhook。

## 选择 Grok 本人窗口桥接

接入候选中的 **Grok Bot · 本人窗口桥接** 使用 `grok-bot`。它优先复用当前房间的有效人物，或其他房间已验证且未固定转发的同一人物与长期入口；确实没有可复用人物时，才准备新的本人入口。独立 Grok 人物不会因为加入 Codex 而自动变成 Codex 的固定群代理。它不生成 MCP 导入配置、不安装 Grok CLI，也不自动修改原生 Bot、创建群或加人。独立的 Grok Build CLI 当前暂不支持，不能替代这个桌面入口。

在你选定的已有 Grok Bot 本人窗口，用获授权的 Windows 本机命令工具真实执行说明中的 `enter`。检查同一房间、本人 `caller_member_id`、`registration=verified` 和 `registered_status=ready`；执行前为 `awaiting_bridge_handshake`，真实握手后才为 `ready_mailbox`。应用进程或说明文件存在都不是握手证明，本机接通也不证明宿主持续在线或原生群已经加人。

## 旧接入说明中的成员不存在

如果 Grok 使用一个旧 `member_id`，而该成员已经不在当前实例中，诊断会显示“当前实例无此成员”，不会创建替代成员或新房间。所选房间仍可能正常存在。

在连接诊断中选择本房间的实际成员，再点击“查看恢复说明”或“查看接入说明”。这些按钮复用现有成员页面；**查看诊断本身不会发放新凭据**，只有你明确点击生成/复制恢复入口或接入动作才处理相应操作。把这份成员说明交给正确的 Bot，保留原房间和实例。不要把入口卡正文、密钥或 MCP 凭据 URL 贴到群聊里。

可以展开“核对旧接入说明”，仅粘贴旧说明中的成员 UUID。服务器会报告它是否存在和是否加入当前房间；不会披露其他房间的成员详情或替你切换过去。

若原聊天室已确认删除，该房间的历史不会被恢复或替代创建。连接凭据属于人物，会转到这位人物仍加入的房间；一个房间都没有时暂停，重新加入后沿用原入口。用户主动撤销的凭据保持撤销。删除本机房间不删除其他房间、共享账号、原生 Bot 或 Grok 群；存在待办、正在处理或结果待核对时，仍须按删除确认流程处理。

## Grok 显示 Windows 宿主未连接

若 Grok 自己报告 `registeredWindowsHost.connected:false`，需要在 Grok 中重新核对并选择实际 Windows 电脑，按它的原生流程授权。Agent Office 无法用本机 daemon 在线来自证该宿主在线，也无法替 Grok 修复注册或授权。

目前没有经过确认的公共宿主配置接口时，不使用 computer use、私有 IPC、浏览器调试接口、Cookies 或用户聊天资料代替这一操作。诊断卡会说明具体边界，不把“请人工核对”写成已自动完成。

## 没有目标群引用或原生加群工具

长期入口正常，并不意味着 Bot 已进入 Grok 群。需要在 Grok 指定真实目标群，并检查当前 Bot 获得的原生群工具。缺群引用时不能按名称猜群，缺原生工具时不能用本机计划冒充已建群或已加入。

`host_reported` 只是本机保存了 Grok 宿主的执行报告；它与独立核验、当前群状态是不同证据。诊断不会自动加人、重建群、重新配置 Grok 宿主或回放旧任务。

## 普通对话能改群，Webhook 例程却找不到群

2026-10-26 的实测中，同一个 Bot 对同一个真实 `channel_id` 调用 `UpdateChannel`，普通对话成功，Webhook 例程返回 `No channel found`。例程通过 `SendToAgent` 转给本人也被原生工具拒绝。这是当前实测的执行上下文差异，不能解释成群不存在、ID 类型不对或整个连接断开。

AO 的群操作现在保存本次所选成员、派发意图、原消息及每位成员的操作回报。关闭建群窗口或服务重启后，尚未派发的请求继续在后台处理；已经派发的请求不会重复提交。旧入群记录、通知受理和 Bot 的中间回复都不能代替本次原生操作回报。

后台任务由已有群成员 Bot 的普通对话执行。该 Bot 的角色包含限定的群管理流程：独立读取 `group-state --session`，核对用户提交记录、原消息、房间和选定成员，然后执行真实 `CreateChannel` / `UpdateChannel` 并逐一 `group-report`。管理任务不委托本机业务模型，也不再次转交。Webhook 只向不同于自己的已有执行方转交一次；不重建已有群，不另建协调 Bot，不让用户手动领取。

2026-10-26 真机验证已完成 AO 后台给已有群追加豆包：原群引用保持一致，Codex 和豆包均回报本次操作，Grok 群成员页显示三位原有 Bot，过程不需要用户二次确认或复制入口。AO 和 Grok 两端新建办公室及对应原生群也已实际验证。运行记录、个人群引用和凭据留在忽略的本机验收资料中，不进入仓库。

一个原生 Bot 可以服务多个办公室。角色文件按真实群引用列出对应的本机入口，每次委托读取最新映射；不能用最后活跃房间或群名猜测目标。豆包的自动连接按当前原生适配能力判断，不再要求为新房间重新完成手动 MCP 握手。

2026-10-27 继续验证了 Grok 群内直接追加豆包：对应 AO 房间同步加入原人物，原群引用未变，当前操作回报完成；另一个测试群中的豆包连续两轮经本机真实模型处理并自动回群。上述验收使用 Windows 实机；手机实体设备不在本次测试范围内。

## 本机服务已关闭

桌面软件关闭服务后可以显示已保存的房间和成员。需要服务器的诊断按钮暂停使用，侧栏显示“离线，查看已保存记录”，不会自动拉起服务。已保存的成员恢复说明仍可查看；没有已有说明时，等你开启服务后再生成。

HTTP MCP 入口需要本机服务运行；已配置的 STDIO 或本机命令长期入口可以按已有授权恢复同一实例。这与 Grok 模型自身能否被唤醒、Windows 宿主是否已连接仍是独立问题。
