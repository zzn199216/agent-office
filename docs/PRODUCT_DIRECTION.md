# AgentRoom 产品定位与交付形态

AgentRoom 让用户已有工具中的 agent 围绕真实项目持续协作。用户交代一次目标后，agent 能找到合适的项目负责人、提交问题、启动处理、继续原讨论并返回结果；用户按需查看进展和介入。

以当前场景为例：Grok 运营一个项目，读取项目事实，遇到疑问向 Codex 提问；Codex 核实后回复；Grok 继续运营，并把用户反馈送回项目讨论。双方沿用自己的工具、项目资料和权限。

## 推荐形态

核心是轻量后台软件，MCP 是 agent 的调用接口，Skill 是使用规则。第一版可以是一个本机后台进程，附带可选的简单网页概览；不需要先做大型桌面客户端。

第一版明确采用单机部署，不购买或部署自有服务器。消息队列、对话绑定、Markdown、状态库和概览均位于用户电脑。Grok 通过其已授权的本机命令工具调用本地入口，Codex 通过本机 CLI/App Server 处理。通知 Grok 可使用其平台已有的 Webhook，不为此搭建自有公网回调服务。

结果优先直接返回本机命令调用；需要异步回报时，通过已授权的本机工具领取或写入固定讨论记录。Grok 本地对话缓存只用于已完成的诊断，不作为产品收件接口。云端模型和运营平台仍使用各自已有的网络服务，这不要求 AgentRoom 购买服务器。

| 层 | 负责什么 | 单独提供时的缺口 |
| --- | --- | --- |
| 后台程序 | 平台适配、启动处理、项目和对话绑定、排队、结果交付、故障恢复 | 需要供各 agent 调用的入口和清晰的使用方法 |
| MCP 或 HTTP 接口 | 提问、查询、等待、讨论历史、回执 | 协议不替代后台运行和可靠状态管理 |
| Skill | 何时找谁、如何组织问题、如何使用结果、什么时候停止 | 指令文件不承担闲置唤醒与执行状态管理 |
| 用户概览 | 讨论、提问、处理状态、回答摘要、失败原因、介入入口 | 展示不替代收发和执行机制 |
| Markdown 记录 | 可阅读的消息、事实资料和讨论摘要 | 文件出现不等于 agent 已开始处理 |

对可用 MCP 的 agent 提供标准工具；对可执行本机命令的 Grok 提供同一服务的 CLI 入口；原生通知通过平台实际支持的 webhook 等机制适配。不要求所有工具使用同一种接入方式。

## 用户获得的产品体验

一次设置绑定项目与 agent；日常通过既有聊天交代协作目标。后台默认安静，问题和回答自动关联到同一讨论。用户打开概览即可知道谁问了什么、是否处理完成、依据是什么、哪里需要介入。

确认消息送达、执行完成、结果消费和原任务继续，分别保留证据。发生临时故障时优先恢复已有记录，不创建重复讨论或重复运营动作。

外部问题不能扩大既有权限。长期授权按用户设定的范围沿用；Skill 的行为规则不作为运行时身份与权限控制的替代。

## 第一版范围

只接 Codex 和一个 Grok Bot，登记一个项目，绑定一条专用讨论。实现提问、执行、回报、追问和可阅读记录，并提供最小的状态概览。

验收：Grok 提问后 Codex 后台回答，Grok 消费结果继续产出草稿；追问复用相同 Codex 会话；重试不重复执行；用户能在界面看清全过程。原生对话续接与固定接收 Routine 的降级必须明确标注。

第一版不扩展为多模型平台、全功能 IDE 或无限讨论系统。通路稳定后，再考虑多人讨论、更多 agent、跨设备与更丰富的任务管理。

## 当前证据与实现状态

Webhook 触发 Grok 并产生回复已经验证；Grok 后台调用 Codex 并得到项目回答已经核对；保存的 CLI 会话能独立读取。可靠回调、原生会话连续性、概览和恢复机制仍需实现验证。

因此可以先以“agent 协作插件”的方式交付，但插件应包含后台运行组件、MCP/CLI 入口和配套 Skill，而不只是一个指令文件。
