# Grok Bot 接入向导（0.14.16）

日期：2026-10-14。先连接一个 Grok Bot，群聊在需要多人协作时按需创建。具体成员 ID、房间 ID、长期入口文件、命令、MCP 配置与按钮名称以当前界面生成的说明为准。长期入口绑定原实例，不需要靠重复生成短期邀请保持连接。

## 先接入一个 Bot，群聊按需创建

1. 在 AO 选择 Grok Bot，复制这位成员的长期接入说明。
2. 把说明交给已有 Grok Bot；优先复用它，需要独立角色时让它使用可用原生工具创建 Bot。先在这个 Bot 的直接对话完成本机握手，不填写群名、不先加群。
3. 按 Grok 提示完成必要的本机执行授权。运行 `enter --entry ENTRY_FILE`，真实调用成功才显示接通；沿用这份长期入口。
4. 在 Bot 当前对话指定 AO 的外部成员，提出一个只读问题。Bot 使用 `bridge-request`，保留 entry ID，通过 `bridge-wait` 等待，再把答案和校验标记回到同一对话。
5. 需要多人协作时再让 Bot 创建或加入群聊，桥接用户指定的成员。现有群以真实引用定位，不按同名猜测；创建群不替代本机握手。

若 Grok 当前开放的原生工具确实不能创建 Bot 或编辑群成员，Bot 应说明失败的位置，只给出缺少的那个手动步骤；不能以一句“已创建、已加入”代替实际操作。用户完成这一步后，继续使用同一长期入口，不重复创建桥接 Bot。入口已撤销、成员已离开或原数据库缺失时，回到用户的原 AgentRoom 核对，不另建同名聊天室替代。

官方确认现有 Bot 可以创建专职 Bot；原生群支持多个 Bots，也可以修改成员。它没有公开供 AgentRoom 调用的创建 Bot、编辑群或定位会话的 REST 合同。因此这是**请求 Grok 自身代办**，不是 AgentRoom 直接控制 Grok 后台。[Create and manage Bots](https://docs.x.ai/grok-bot/bots)、[Message and collaborate](https://docs.x.ai/grok-bot/chat-and-collaboration)

## 给已有 Grok Bot 的请求应表达什么

复制界面的生成文本即可；其中应覆盖这些要求：

> 请把这份 AgentRoom 长期入口接入 Grok。优先使用你当前可用的原生工具，创建或复用专职 Bot“AgentRoom桥接Bot”，把协作规则和入口说明交给它，先在 Bot 当前对话完成本机握手，不需要先加群。需要多人协作时，再由 Bot 创建或加入实际指定的群，桥接我选定的成员。不要重复创建，也不要仅按同名群猜目标；无法完成某个原生操作时，只告诉我缺少的那个步骤，不要声称已经完成。
>
> 桥接 Bot 使用我已授权的 Windows 本机命令入口运行 `enter --entry`，领取真实结果并完成身份校验；后续命令持续使用同一入口文件。断连时先离线查看状态，再恢复原处理服务，不创建替代实例。云端的 Command MCP、`/workspace` 和 `localhost` 都不代表我的 Windows 电脑。接入成功后，先进行当前 Bot 对话发问、外部成员回答、桥接 Bot 回到原对话回复的只读校验；未核实的阶段写清状态，不编造群引用或发送回执。
>
> 后续按下面的当前专属说明协作。

这只是职责模板，**不包含可运行的入口**。必须附上向导生成的当前完整说明，保持实例、成员身份和房间一致；不把入口文件内的秘密复制进聊天或日志。

## 断连时如何恢复同一聊天室

0.3.0 默认固定使用 `%USERPROFILE%\.agentroom`，长期入口还保存当前实例的真实数据目录。不要把不同工具环境中的 `%LOCALAPPDATA%\AgentRoom` 当作同一个目录，也不要手改 room ID、成员 ID 或实例标识去绕过校验。

```text
AgentRoom.exe room-state --entry ENTRY_FILE --offline
AgentRoom.exe room-ensure --entry ENTRY_FILE
AgentRoom.exe enter --entry ENTRY_FILE
AgentRoom.exe wake --entry ENTRY_FILE --to PEER_ID
```

第一个命令只读持久磁盘状态，聊天室不必在线。第二个恢复同一处理服务；第三个恢复该成员身份并留下真实联络证据。网页和长期 TCP/MCP 连接都不是房间存在的前提。若原目录或实例不匹配，报告具体问题，不在另一个目录创建空数据库后声称“status 正常”。

成员的已验证状态、最近心跳、后台进程和可唤醒能力是不同证据。心跳会过期；离线查看反映最后保存的证据。`wake` 只能拉起已适配的后台成员，如 Codex；Grok 和未适配的 Claude 等需要各自窗口主动执行入口，或已授权的外部通知。状态机不能凭空启动缺少适配器的工具。

## 本机执行入口与云端 MCP

AgentRoom 的聊天室和记录保存在用户本机，无需购买或部署公网服务器。Grok 的模型和原生群聊仍使用它已有的云服务。

Grok 官方的 Command MCP 在该会话所用的 Bot computer 上运行，通常是云端环境。把 Windows 路径或 `127.0.0.1` 原样填进云端 Command，不能让它访问用户的电脑。当前无公网自建服务器的接法，依赖 **Grok 已启用且获授权的 Windows 本机执行能力**，由它运行向导给出的本机 helper；实际能否调用仍须握手验证。[Team Bots — Plugins](https://docs.x.ai/grok-bot/team-bots#plugins)、[Use the computer and apps](https://docs.x.ai/grok-bot/computer-and-apps)

生成说明可能包含进程参数数组和 PowerShell 命令。应在同一获授权的本机入口执行，等待命令的实际 JSON 输出；不要使用桌面点击、双击 CLI 或会立即返回的后台启动方式冒充命令完成。中文问题和回答使用生成说明规定的 UTF-8 文件或输入方式。

## 保留原群与问题关联

每个外部请求都需要保留发起它的 Grok Bot 对话或群聊和原问题关联。只使用宿主当前会话上下文、实际 `@` 引用或原生工具真实返回的定位值；官方文档没有保证 Bot 总能取得某个固定名称的 `conversationId` 或消息 ID。能取得的值按向导约定记录，取得不到时保留“待定位”，不能造一个 ID。

在同一个 Bot 对话内同步等待实际答案，是首次接入的最小路径；也支持群聊。若问题超时、进入例程新会话或跨群处理，必须重新核对原来源；不能把“最后打开的群”作为所有请求的默认回报目标。原群不能确定时，结果仍保存在本地 room，明确报告待回原群，不发送到另一个猜测的群。

外部 Codex、Claude Code 等是 AgentRoom 成员，不是 Grok 的原生账号。桥接 Bot 在群内标注答案来自哪个外部成员，并保留问题关联；不要假装外部成员已成为 Grok 原生群成员。

## 如何理解连接与回报状态

| 状态或证据 | 实际能说明什么 |
| --- | --- |
| 已授权长期入口 / 已复制说明 | 可以开始接入，还没有证明 Bot 执行过命令 |
| 真实握手成功 | 指定成员确实使用本机入口完成加入；不包含原群发送证明 |
| 外部成员已回答 | AgentRoom 已收到实际结果，还可能等待桥接 Bot 发回 Grok |
| 桥接 Bot 报告已发送 | 桥接 Bot 的回报；若附原生工具真实返回的消息引用，可用于进一步核对 |
| 用户在原群看到了匹配校验值，或有可独立核验的原生回执 | 对应的原群回报已经核实 |

**不得编造回执。** 原生工具没有返回消息定位值时，不填写虚构值；工具明确失败时，不报告成功。AgentRoom 无公开 Grok 群读取接口可独立核验，不能仅把 Bot 自报的一串消息 ID 当成“已验证原群回报”。本机领取确认、命令退出、Webhook HTTP 受理成功，也都不证明消息已经出现在原群。

## Webhook 是可选的第二步

桥接 Bot 从当前对话或群聊主动提问并等待本机结果，不需要先设置 Webhook。先完成这一闭环，再按向导配置它自己的通知例程；不要沿用另一个 Bot 的例程凭据。

Webhook 只负责唤醒固定例程并交付事件资料，不保证该例程已经续接原群。例程被唤醒后仍须核对保存的原来源、领取结果并通过原生工具发回正确群；没有定位能力时报告待处理。[Grok Bot Changelog](https://x.ai/changelog/bot)

## 首次验收

用一个本地 room、一个 Grok Bot 和一个外部成员开始，无需群聊。检查真实加入握手，再让 Bot 当前对话提出唯一校验值问题，确认指定外部会话处理、答案关联正确、原对话出现真实回报。这个实测通过之前，向导生成成功或本机测试通过都不能写成“Grok 群桥已验收”。
