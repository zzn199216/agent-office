# AgentRoom 验证计划

本计划用于后续实现和集成验收；本轮仅执行了标为已完成的研究检查。

验收目标是“一次真实提问自动处理，追问复用讨论，回答返回可识别的来源任务”。支持声明、请求 2xx、文件产生和模型最终文本分别只能证明其中一段。

## 研究基线 已完成

- 核对目录、项目登记、Codex 与 Grok Bot 文件版本。
- 当前 Codex 导出 schema，记录相关接口及字段 hash。
- stdio App Server 初始化和目录限定的 `thread/list` 成功。
- 阅读官方触发说明，静态检查固定版本 Grok bridge。
- 生成本轮设计、协议示例和证据文件。

没有创建或恢复聊天，没有启动模型，没有安装 hooks/Skill，没有配置 Routine，没有调用真实 webhook，没有对 X 执行任何动作。

## 第一阶段 先验证接入差异

| 检查 | 通过证据 | 不通过时的处理 |
| --- | --- | --- |
| Grok 能访问入口 | 已认证的无模型收件测试，正确关联 ID | 选择私网或 HTTPS 入口，不暴露 App Server |
| 本账号有 Webhook Routine | 界面确认可配置，试验 payload 到达指定 Bot | 保留 tool_result 方式；不伪称后台唤醒 |
| Grok 原对话是否可续接 | 原对话中出现相同讨论 ID 的结果并继续任务 | 固定接收 Routine + 任务记录，明确 fallback |
| Codex 聊天在桌面可见 | 创建专用试验聊天后，观察项目归属、名称和内容 | 先验证项目关联方式；不能只改 cwd 宣称完成 |

本账号 UI 配置和实际事件行为必须独立检查。官方已有 webhook 不证明当前账号已经连接。

## 第二阶段 最小问答

登记一个项目的资料，只要求 Codex 回答一个只读问题。使用一条专用聊天，不接管开发聊天。

通过标准：

1. Grok 提问带上稳定重试键和讨论 ID。
2. 接收程序只启动一轮，保存原生 thread/turn ID。
3. Codex 核实资料，并在完成事件后保存回答。
4. Grok 领取正确答案，回执 consumed，并产出运营草稿。
5. 整个过程可通过消息、状态和两端原生记录对应起来。

无数据时必须回复未知，并保留问题，不使用示例内容填充真实事实。

## 第三阶段 持续讨论

- Grok 追问同一问题：Codex thread ID 不变，turn ID 更新。
- 新业务项目或独立主题：新 discussion ID，不复用其他项目聊天。
- 同时提交两问：同讨论顺序处理，不覆盖或随意中断。
- 原生 ID 被删：只有确认删除且符合既定策略才重建，保留关联历史。
- 无法访问、来源不明或多个同名候选：明确待协调状态，不能自动猜选。

## 第四阶段 恢复与去重

| 场景 | 必须得到的行为 |
| --- | --- |
| 相同请求重投 | 返回既有请求，不再执行模型 |
| 相同重试键但正文改变 | 拒绝冲突，原问题保留 |
| 创建线程响应丢失 | creation_uncertain；先协调，避免第二次创建 |
| 模型运行时程序重启 | 查已有 thread/turn 证据，不能直接再跑 |
| 完成后通知失败 | 回答保留，仅重试交付 |
| 通知到达但 Grok 尚未消费 | accepted，不标 continued |
| MD 导出失败 | 修复 outbox，不重新运行模型 |
| 重复回报 | 相同 delivery ID 只消费一次 |
| 本机离线 | 问题保留；恢复后处理，Grok 获知 pending |
| 需要用户输入 | waiting_input，原请求不被当作成功 |

另外检查未登记路径、未授权项目、未知接收方不能被访问，日志不含凭据。测试可使用离线假适配器验证状态机；真实平台行为仍须原生证据。

## 第五阶段 运营闭环

先只生成草稿，验证“项目事实 → 运营内容 → 项目疑问 → 答复 → 修改草稿”。之后按用户对 Grok 的实际授权验证发布和反馈回流。

X 发布不是本轮或最小问答的默认动作。发生重试时，运营方应检查已有帖子记录，不再次发布相同内容。

## 放行条件

所有最小问答证据可关联；追问沿用相同 Codex 聊天；恢复与重试不重复执行；Grok 返回模式明确；用户能定位两端处理记录。若使用接收 Routine 降级，只能宣称任务状态恢复，不能宣称原生对话无缝续接。

第一版能否继续实施，优先由第一阶段的网络、Grok 续聊和 Codex 桌面显示结果决定，而不是先安装全套系统再发现不兼容。
