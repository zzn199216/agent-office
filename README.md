# Agent 办公室 · Agent Office

把 Codex、豆包等 AI 接入同一间本地办公室，通过文字聊天或像素办公室协作。离开电脑后，可以在 Grok 的原生群聊里继续向本机 AI 派发任务、接收回答，无需为 AO 自建公网服务器。

项目目前为 **Windows x64 开发预览版**。最新开发代码在 [claude/onboarding-redesign](https://github.com/zzn199216/agent-office/tree/claude/onboarding-redesign)，当前版本以 [package.json](package.json) 和窗口显示的实际服务版本为准。

## 现在可以做什么

- **两端管理聊天室**：在 AO 或已接通的 Grok Bot 中创建办公室及镜像群，给已有群追加选定成员。
- **持续自动协作**：支持自动处理的成员收到任务后执行并回写回答；豆包默认走自动连接，无需用户逐条领取。
- **一位成员参与多个房间**：复用已有身份和连接，每个 Grok 群对应自己的 AO 房间。
- **看得见的工作状态**：文字与办公室视图共用消息，工作时显示进度摘要；接入卡片放在对应对话气泡里。夜间默认亮灯，也可手动关灯。

## 快速开始

1. 按下方[本地开发与测试入口](#本地开发与测试入口)构建并验收，然后双击 **`dev/AgentOffice.exe`**。
2. 选择项目文件夹，创建聊天室。在「接入成员」中选择已安装、已登录的 AI，按界面完成首次连接。
3. 先发一条简单问题，确认目标 AI 的实际回答回到当前房间，再开始日常协作。
4. 需要远程使用时，接通已有 Grok Bot，再打开房间顶部的「协作」→「Grok 镜像群」，选择 AI 并创建群。也可以直接在 Grok 中提出建房或加人请求，见下方流程。

打开软件会启动本机服务。**需要后台继续工作时请最小化窗口；关闭软件会停止服务。**

## 连接成员

在「接入成员」中扫描本机，再选择需要的成员。已运行的候选优先展示；未完成真实验证的接入尝试不占办公室工位。接通秘书后自动进入办公室，失败时保留原进度并给出下一步。

| 成员入口 | 实际能力与条件 |
| --- | --- |
| Codex、Claude Code、Qwen Code、Gemini CLI | 专用后台协作会话；沿用各自可用的账号或 API 配置，须完成实际验证。 |
| Qwen、豆包桌面 | 支持的 Windows 客户端版本可通过「连接本人对话」保存独立人物会话，自动派发并回写回答；首次需开启本机连接。 |
| Grok Bot | 复用已有 Bot 的本人窗口桥接；需要可用的本机执行入口和真实握手，群聊不是接入前提。 |
| Claude 桌面及其他 MCP 客户端 | 导入、启用本机 MCP 后领取和回复消息；自动唤醒能力须按客户端单独验证。 |

连接属于办公室人物，加入新房间、删除旧房间或升级软件不要求重新导入 MCP。原 `AgentRoom.exe`、`agentroom_*` 工具名和 `.agentroom` 数据路径保留兼容。安装、登记、进程存在与真实接通是不同状态；实际回复仍以当前验证结果为准。

在聊天里请求接入成员时，操作卡片显示在对应回复气泡内，并持续更新连接状态；回复到达前，先显示在提问气泡内。历史回复是当时的记录，当前状态以卡片为准。接入完成不代表 Grok 镜像群已创建或原群回传已验证。

首次接通 Grok，需要在所选 Bot 中完成 AO 提供的连接说明，并授权它使用这台 Windows 电脑的本机工具。已有连接可跨房间使用；云端 MCP 中的 `localhost` 不等于这台电脑。具体步骤见 [桥接指南](docs/BRIDGE_SETUP.md)。

Codex 使用原有登录配置与 AO 专用工作会话，不接管正在使用的个人对话。Qwen Code 与 Qwen 桌面使用不同的认证入口，不能把桌面已登录当成 CLI 已认证。各客户端的支持版本、权限和连接要求见下面的指南。

## 在 Grok 中继续协作

### 从 AO 创建或更新群

打开房间顶部的「协作」→「Grok 镜像群」，选择要加入的 AI、填写群名并提交。已有绑定群时，使用「更新所选成员」追加成员。已接通主动通知的 Grok Bot 会自动处理请求，关闭该面板后任务仍在后台继续；服务重启后，尚未派发的请求可继续处理，已派发的请求不会重复提交。

首次尚未启用主动通知时，面板提供交给 Grok 的连接说明。完成首次配置后，日常建群和加人无需反复复制说明或手动领取任务，也不依赖 computer-use。

### 从 Grok 创建房间或加成员

在已接通的 Grok Bot 对话中，可以直接说：

> 在现有项目中新建一个「产品讨论」聊天室，并创建对应的 Grok 群，加入 Codex 和你。

在已有镜像群中，可以向负责群管理的 Bot 说：

> 把已有的豆包也加入这个群和对应的 AO 聊天室。

建房会准备对应的 AO 房间；加人复用已有原生群、成员身份和自动连接。用户不需要查找房间 ID、入口文件或重新配置 MCP。普通工作问题直接 @ 对应成员，回答由指定的本机 AI 实际处理后返回当前 Grok 群；同一成员参与多个群时，按真实群引用选择对应 AO 房间。

### 出门前确认

使用同一 Grok Bot 账号，并保持运行本机 AI 的 Windows 电脑联网、不休眠，AO 服务、Grok 本机连接及所需客户端可用。先在目标群发一条问题，确认「Grok 发问 → 指定 AO 成员实际回答 → 同一 Grok 群收到结果」完成。

豆包默认使用经过版本校验的自动连接，当前适配保留 2.32.4，并加入 2.33.3 的精确资源校验；未知客户端版本会提示修复。仅能手动领取消息的 MCP 信箱不算远程自动协作就绪。各 AI 的账号、额度和执行权限仍由对应客户端提供。

## 最近实测情况

2026-10-26 至 2026-10-27，在 Windows 实机上验证了以下流程：

| 流程 | 实际结果 |
| --- | --- |
| AO 新建房间和 Grok 镜像群 | 原生群实际可见，复用已有 Codex Bot。 |
| AO 后台给已有群追加豆包 | 原群引用保持一致，实际成员页及本次操作回报均确认加入；无需用户手动领取或再次确认该加人请求。 |
| Grok 端建房和群内加人 | 对应 AO 房间和原生群均完成创建、追加已有豆包。 |
| 豆包持续自动回复 | 同一群连续两轮由本机豆包实际回答并回群，另一群也完成独立往返。 |
| 多群路由 | 新群消息进入对应 AO 房间，原有群的 Codex 仍回到原房间。 |
| 夜间办公室 | 默认亮灯，手动关灯和重新开灯有效。 |

本次未直接操作手机实体设备。上述结果是对应版本和连接环境的实测记录，不代表所有客户端版本均已验证。通知受理、Bot 的中间回复与实际建群或回答完成分别记录，只有本次真实操作回报才能更新群操作结果。

## 使用与资料

文字与办公室视图共用房间、成员和消息。Enter 发送，Shift + Enter 换行；聊天支持 Markdown 和图片，图片派发能力取决于成员适配器。已授权的日常协作自动继续，需要确认的操作放在对应成员的最新对话中。

房间可归档、恢复或删除；删除前显示本房间的未完成工作并要求确认。其他房间与共享连接保留。运行记录、成员凭据与 MCP 配置留在本机，不属于 Git 源码。

## 本地开发与测试入口

需要 Node.js 22.13+、Windows x64 和 WebView2 Runtime。

```powershell
npm ci
npm run verify:dev
```

`verify:dev` 是本机和 Windows CI 共用的交付验收入口：语法检查 → 桌面 SDK → 完整 Node 回归 → 六条核心流程及界面验收 → 开发包构建 → 打包后的 MCP、启动恢复和文件校验。首次运行自动安装锁定版本的 Playwright Chromium，并下载固定版本、校验 SHA256 的官方 WebView2 SDK；后续复用缓存。任何失败、跳过的回归或未完成的核心流程都会返回非零退出码，后续步骤停止。

| 核心流程 | 必须观察到的结果 |
| --- | --- |
| 首次接入 | 从空白首页创建项目和房间，再从接入按钮复制地址，经过实际 MCP 初始化、工具发现和成员工具调用；复制或发现工具本身不能显示已连接。 |
| 已有成员加入新房间 | 从界面创建新房间并接入已有成员；成员及凭据不重复，原地址可访问两个房间。 |
| 任务进度和回复 | 从输入框发送消息、成员领取、办公室显示进度、点击回到原任务；实际 MCP 回复关联原消息并清除进度。 |
| 断线及重启恢复 | 页面显示断开；服务以同一数据和地址重启且更换控制凭据后，页面恢复，旧成员地址能回复重启前的消息。 |
| 退出和删除隔离 | 从界面移出共享成员、重新加入并删除房间；其他房间仍能收到同一成员对新消息的回复。 |
| 夜间及窄窗口 | 夜间默认开灯，开关与刷新持久化有效，390px 窗口可点击灯光按钮并发送、查看回复，无页面横向溢出。 |

验收使用隔离数据和模拟外部 MCP 客户端，走真实 AO 服务与界面，不操作个人客户端或调用付费模型。它不代表当前豆包、Grok 等真实客户端已经接通。工作摘要更新和多成员布局另由现有办公室界面回归覆盖。浏览器依赖遵循 [Playwright CI 安装方式](https://playwright.dev/docs/ci)，不读取开发者工具缓存。

网页与桌面共用界面和 Node 服务，但桌面的 WebView2 宿主还负责窗口、文件夹选择和服务启停。修改这些功能后，需要用隔离数据打开实际开发包，补测选择/取消文件夹、剪贴板、最小化恢复和关闭重开；浏览器通过不能替代这些检查。添加项目时可直接填写路径；选择文件夹后，空白项目名自动使用文件夹名称。

最近一次结果在 `output/verify-dev/latest.json`，该文件指向本次源码指纹、各阶段日志、六条流程结果和截图。开发分支 push、PR 及手动触发均执行同一入口；CI 无论成功或失败均保存本次验收证据，只有成功才上传开发包。开发中可以运行 `npm run check`、针对性的 Node 测试或 `npm run test:core` 快速检查；这些不能代替交付前的完整验收。

验收通过后直接双击 **`dev/AgentOffice.exe`**。只需构建时仍可运行 `npm run build` / `npm run build:dev`；它们更新同一个 `dev/` 目录，不生成 ZIP，也不代表已经完成验收。源码、依赖和构建过程不依赖旧项目目录。

打开软件自动启动本机服务；关闭软件停止服务。需要后台继续处理任务时，使用窗口最小化按钮，页面刷新、动画和 WebView 会暂停，恢复窗口后重新读取进度。独立命令行服务仍可用于开发：

```powershell
npm start
# 或只启动服务：npm run serve
```

正式分发包按需执行 `npm run build:release`，产物进入 `release/`。完整发布验收和已有隐藏发布任务的说明见 [本机发布与诊断](docs/RELEASE.md)。普通开发无需创建正式包或注册发布任务。

## 项目维护

`src/` 为本机服务和适配器，`web/` 为界面与运行素材，`desktop/` 为 Windows 宿主，`tests/` 为回归测试，`scripts/` 为构建与验收工具。当前架构与检查入口见 [开发交接](docs/HANDOFF.md)。

每个完成并通过检查的改动做一次 Git 提交，从开发分支推送 GitHub；用提交回退源码，再重新构建固定开发版。依赖、SDK 缓存、打包文件、测试输出、数据库和个人配置均不提交。Git 历史保留旧版本和设计资料，不在当前目录重复存放历史包。

当前尚未开放给用户，不引入用户账号数据库、生产数据迁移或长期备份流程。程序运行所需的本机状态与连接配置仍正常保留；隔离测试使用可丢弃的临时数据。
